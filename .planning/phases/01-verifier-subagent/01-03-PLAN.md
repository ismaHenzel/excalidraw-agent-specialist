  IMPORTANT: For the containing-shape lookup to match, the helper computes the text bbox using estimated_width. The rectangle (sx=200, sy=200, sw=180, sh=80) does NOT enclose the text bbox (right edge 240+312=552 > 380). Per the implementation in Plan 01 Task 2, `_find_containing_shape` requires `sx + sw >= tx + tw`. To get a containing match, either (a) widen the rectangle to encompass the text bbox (defeats the test), OR (b) make the rectangle the "smallest containing" by enlarging it to 400×100 so it encloses the 312-px-wide text bbox AND fires the overflow. Use option (b): set the rectangle to width=400, height=100 (so it ENCLOSES the text bbox), and set the rectangle's id to "r_container". The text width is 312 px and the container width is 400 px — those would NOT overflow. Re-tune so the overflow fires: text "Databricks Workspace Configuration Setup" (40 chars × 0.6 × 20 = 480 px) inside a container 400 wide. text bbox right = 240+480 = 720; container right = 200+400 = 600 — bbox NOT enclosed; container_lookup fails; overflow check skips.

  CORRECTED DESIGN (must be tested by Plan 01's helper before committing the fixture):
  - Rectangle "r_container": x=200, y=200, width=400, height=100, roughness: 0, roundness: {type: 3}.
  - Text "t_db": x=240, y=228, text="Databricks Workspace Setup Configuration" (40 chars × 0.6 × 20 = 480 px estimated width) BUT this exceeds the container's right edge (600), so the lookup fails.
  - ALTERNATIVE that satisfies both "text bbox enclosed by container" AND "estimated_width > container_width":
    The helper computes text bbox using estimated_width which equals overflow-implying number. If estimated text width > container width, the text bbox (right edge) cannot fit inside the container. The containing-shape lookup REQUIRES the text bbox to be enclosed; this is a contradiction unless we interpret the lookup more leniently.
  - PRACTICAL DESIGN: Use a 2-rectangle nested structure. The OUTER rectangle is large enough to enclose the text bbox; the INNER rectangle (the one we want flagged) is smaller and SHOULD have contained the text but doesn't. The helper finds the SMALLEST containing shape — if the inner rectangle does NOT enclose the text bbox, the next candidate is the outer rectangle, which DOES enclose it. The overflow check then compares the text's estimated width against the outer rectangle's width. To make THAT fire, the outer rectangle must itself be narrower than the estimated text width, but then it doesn't enclose the text bbox either, breaking the lookup.

  The geometric trap: the helper's `_find_containing_shape` enforces "container bbox encloses text bbox (using estimated_width)". If overflow exists, by definition the text bbox is NOT enclosed by the would-be container — so the lookup fails and the check skips. THIS IS A DESIGN ISSUE in the helper's specification.

  RESOLUTION (planner authority — applies to Plan 01 Task 2 retroactively AND to this fixture design): the containing-shape lookup compares the text's POSITION (text.x, text.y, text.fontSize as height) AGAINST the container's bbox using JUST the text-element's declared `width` / `height` fields (the element's own bbox as stored in JSON), NOT the helper-computed estimated_width. Excalidraw text elements DO carry their own `width` / `height` (the user-set bbox); the overflow check is `estimated_width > container.width` where estimated_width uses MONOSPACE_ADVANCE_RATIO * fontSize * len(text), and the containing-shape lookup uses the text element's STORED width to determine bbox containment. This way: the stored text width can be 100 (a small bbox the user drew), enclosed by the 180-px container; the helper's estimated width is 312, exceeding 180 — overflow fires.

  Three of the five keys vary by environment — diff is normalized to ignore them:
  - `checked_at`: timestamp; always changes
  - `source`: absolute path to .excalidraw; varies by checkout location
  - `png`: absolute path to PNG; varies by checkout location
  Expected-report.json may use placeholder strings for these three fields. The self-test diff command is:
    diff <(jq 'del(.checked_at,.source,.png)' expected-report.json) <(jq 'del(.checked_at,.source,.png)' generated.json)
  Exits 0 (no diff) when the visible fields match.

  PRACTICAL CHOICE for committed expected-report.json files: use placeholder strings for the three volatile fields (so the file reads naturally as documentation):
    "checked_at": "<IGNORED-IN-DIFF>",
    "source": "<IGNORED-IN-DIFF>",
    "png": "<IGNORED-IN-DIFF>"
  The diff strips these from both sides; the placeholders only document that they're not compared.

  expected-report.json files in this plan capture the STRUCTURAL issues only (the 4 error + 4 warning checks the helper emits). The VISUAL issues (5 checks the subagent emits multimodally) are NOT in the structural expected-report.json — they are added by the subagent at runtime and the manual end-to-end test (Task 4 checkpoint) covers them.
